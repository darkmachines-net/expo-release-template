# Provider execution

`worker.mjs` is the fixed workflow entry point. `github.mjs` owns immutable plans, confirmed-operation receipts and retry reuse; a failed attempt never prevents a fresh release. Consumers supply metadata and validation hooks, without deployment/recovery wrappers.

`continuous.mjs` checks the beta promotion reviewer boundary before staging. `development.mjs` owns credential-free native inspection/export and separate authenticated EAS build/publication. `development-build.mjs` reconciles automatic clients against EAS by full native compatibility across commits, using an inert project for provider reads and asynchronous polling while cloud builds run. `development-history.mjs` records `expo-development-v1` deployment intents and confirmed provider links independently of release reservations. Only successful statuses advance per-platform native/bundle baselines. Same-attempt duplicate operations are rejected; retries reuse confirmed results. Automatic builds recover compatible EAS clients after a lost GitHub acknowledgement; an unconfirmed provider acknowledgement can still cause redundant delivery. The [consumer contract](consumer/README.md#continuous-delivery-to-beta) owns setup and tester instructions.

`deploy.mjs` supports the existing WireGuard webhook. `gcp.mjs` supports a provisioned Cloud Run API, optional private worker, migration job, Artifact Registry repository and Firebase Hosting site. Set `server.deployment.provider` to `gcp` with `project`, `region`, `api`, `migrationJob`, `hostingSite`, `registry`, and the public HTTPS `origin`. Add `worker` only when the application owns a separate worker service. Optional `readinessPath` selects an absolute path (default `/api/ready`); query strings, traversal, and foreign origins are rejected. Infrastructure and OAuth/store configuration remain with the application.

## Terraform before delivery

[terraform.mjs](terraform.mjs) owns optional Google-authenticated infrastructure planning and apply. Configure `profiles.<profile>.terraform` with `directory` (for example `deploy/gcp`), an exact Terraform `version` (for example `1.13.5`), and dedicated `planEnvironment` and `applyEnvironment` GitHub environments. Configure every profile that targets that infrastructure, including beta when its backend is production. Commit the remote backend configuration and `.terraform.lock.hcl`; use the default Terraform workspace and immutable module references. The workflow accepts no arbitrary Terraform arguments, targets, destroy mode, or backend overrides.

Both environments supply `GCP_TERRAFORM_WORKLOAD_IDENTITY_PROVIDER` and `GCP_TERRAFORM_SERVICE_ACCOUNT` variables. Bind each identity to the repository, protected default branch and exact environment. The planner needs infrastructure reads and remote-state locking; the applier needs the module's infrastructure permissions. These identities are separate from `GCP_RELEASE_SERVICE_ACCOUNT`. The caller grants `id-token: write`. Providers and reviewed Terraform configuration execute with Google ADC only, in dedicated jobs after tool setup; application install hooks and publishers receive none of these credentials.

The plan environment supplies the `TERRAFORM_VARS_JSON` secret, a complete JSON tfvars object. Set the same `TERRAFORM_PLAN_KEY` secret in both environments: a base64-encoded 32-byte random key. Saved plans contain sensitive inputs, so only an AES-256-GCM encrypted artifact is uploaded, bound to the immutable release plan, source, toolkit, run and destination. Decrypted plans and inputs exist only in temporary directories and are removed on exit. Keep the key unchanged until outstanding runs finish; an unavailable artifact or key requires a fresh release. Terraform's human-readable plan is shown in the job summary for review; declare confidential Terraform values `sensitive` so Terraform redacts them. Do not put secrets in resource names or other public plan fields.

Every configured delivery refreshes and plans the full environment, including infrastructure-only changes and live drift when application inputs are unchanged. Exit 0 skips apply; exit 2 exposes the saved plan for approval; every other exit fails. Inspect resource and field changes, replacements and deletions in the summary before approving. The apply environment must require reviewers and differ from planning, deployment and earlier release/development approvals. Apply executes that exact saved plan with state locking and the committed provider lockfile; it never silently replans. Terraform configuration must preserve live images and traffic while infrastructure is updated, leaving rollout to the deployment worker.

Failed Terraform commands retain a separate `terraform-plan-diagnostic-<attempt>` or `terraform-apply-diagnostic-<attempt>` artifact for three days. It contains only `terraform.failure.enc`, encrypted with `TERRAFORM_PLAN_KEY` and bound to the complete immutable release plan in a diagnostic-specific authentication context. Logs show only the failed command and exit code. An authorized operator with the key can call `readTerraformDiagnostic(file, plan, env)` from this module's `terraform.mjs`, supplying the run's immutable `plan.json` release asset. The result contains the command, exit code, and bounded tails of each output stream; treat these decrypted details as confidential and do not copy them into logs or issues. Diagnostics cannot be restored or applied as release plans. Keep an operator-controlled copy of the key if diagnosis is needed; GitHub secrets cannot be read back.

The serialized delivery workflow holds the release queue across plan, approval, apply and deployment. Other operators must coordinate access to the same backend; Terraform locks protect each state operation and reject stale saved plans if state changes during approval. Server migrations/deployment, store submission and OTA publication require successful infrastructure checks/apply even when no server change is selected. Builds remain parallel. Infrastructure checks do not force application version bumps or advance application baselines. Confirmed apply receipts are reused on job retries; failed, uncertain or partially applied plans may be stale, so start a fresh release to refresh and review a new plan. No plan or provider receipt is overwritten.

## Application deployment

The protected deploy environment supplies `GCP_WORKLOAD_IDENTITY_PROVIDER` and `GCP_RELEASE_SERVICE_ACCOUNT`. Bind federation to the consumer repository, its protected default branch and that exact environment. The caller workflow must grant `id-token: write` as well as its existing permissions. The release identity needs registry write, Cloud Run deploy/job execution, service-account use for the three runtimes, and Firebase Hosting administration. It needs no database password or AI key. Artifact production and CLI installation finish before federation credentials are admitted.

Deployment consumes the confirmed GHCR publication digest, copies it without digest changes into Artifact Registry, runs the migration job, verifies startup probes and revision digests, and checks the staged API's readiness path. Each configured service receives a release tag with zero traffic before verification: Cloud Run otherwise leaves a worker revision retired when traffic is pinned to its predecessor. Worker tags retain the service's IAM restriction. Every readiness path must report `{status:"ok",version,revision}` for the deployed release and `K_REVISION`; a custom path never relaxes that contract. Only then does deployment switch traffic and publish Hosting with `pinTag:true`. Public HTTPS readback must match the same API revision. Native and OTA jobs remain gated on deployment success. API-only receipts omit `workerRevision`.

An uncertain deployment has no success receipt. A job retry may repeat those provider operations; migrations must be additive and idempotent. Confirmed entire operations are reused by `perform`. Databases are never rolled back automatically. Retain compatibility with older clients and rolling service revisions.

Container smoke configuration supports `services.<name>.ready` (a command run inside the dependency) and `initialize` (a command in the exact built application image, before API startup). These use an owned Docker network and disposable containers without publication credentials. No production migration is run during smoke validation.

## iOS store signing

iOS cloud builds omit `--freeze-credentials` so the pinned EAS CLI can repair invalid provisioning profiles through its normal credential setup. Assign an App Store Connect team API key with provisioning access to the app in EAS, following [Expo's CI signing setup](https://docs.expo.dev/build/building-on-ci/#optional-provide-an-asc-api-token-for-your-apple-team). Android builds retain the flag. The toolkit delegates credential validation and repair to EAS; it has no separate signing preflight or Apple API adapter.
