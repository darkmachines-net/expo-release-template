# Release engine maintenance

This repository owns three fixed release paths consumed by Expo application repositories. Keep authored implementation plus consumer integration below 3,000 physical lines; count existing application builders separately and transparently.

- Preserve immutable current-format plans and provider receipts. Legacy records are intentionally unsupported after cutover. Failed or uncertain prior operations must never block a fresh release; redundant delivery after a lost acknowledgement is an accepted tradeoff. Reuse confirmed operations on explicit job retries; keep duplicate protection within each workflow attempt and advance baselines only on confirmed success.
- Keep component selection independent of GitHub workflow success, and keep native runtime compatibility separate from store submission status.
- Keep the pure engine dependency-free. Ship the complete CLI as executable JavaScript for Windows and Linux with Node 22.14 or later.
- Keep live documentation beside its owner: use code comments for implementation contracts and a module-scope README.md for module usage or architecture. Link to the owning module instead of duplicating its documentation. Do not check in docs/ files, generated documentation, change summaries, migration reports or other point-in-time documentation; keep change history in Git and pull requests. Group related code into cohesive subdirectories when that gives documentation a clear owner.
- When adding or updating any authored code file, add or update its file-level documentation comment. When adding or updating any public/exported callable (including returned API methods), add or update useful function-level JSDoc describing its behavior and relevant inputs, outputs and constraints. Use native comments for YAML and non-JavaScript scripts; JSON and generated snapshots are exempt.
- Run npm run check before handing off changes. ESLint's existing JSDoc rules enforce file overviews and descriptions on named functions/methods, including public APIs, across JavaScript source, scripts, tests and examples; do not replace them with custom documentation-checking scripts.
- Add meaningful tests for changed selection, stage ordering, recovery, identity, or artifact-validation behavior.
- Consumers install the root package through a full-SHA Git dependency and pin the reusable workflow to the same SHA. Update pins and locks with scripts/sync-engine.mjs. Do not copy engine source or add consumer lifecycle orchestration.
- Keep source validation and artifact production free of publishing credentials. Shared workers own signing, approval and provenance boundaries; EAS cloud build configuration evaluation retains its explicitly documented authentication boundary.
- Never dispatch a live release as a side effect of testing the engine.
